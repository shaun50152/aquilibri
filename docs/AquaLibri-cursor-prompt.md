You are implementing the AquaLibri "Equilibrium Instrument" design in this repository (shaun50152/aquilibri) for a live HackUTA demo. The frontend is plain HTML, CSS and JavaScript served by FastAPI. Do not add a framework, bundler, npm build step or CDN script. Two people must be able to maintain it.

PRODUCT IN ONE PARAGRAPH
AquaLibri schedules AI batch jobs across data centers to cut water withdrawal while respecting GPU capacity, deadlines and cost. The portal lets a user submit a job and follow it to a sample result. The operator page shows the fleet, previews a new schedule (routine within a cost budget, or emergency redistribution when a site has a water cap), explains it with Gemini, compares before and after, and applies or discards it. All data centers and GPU execution are simulated and the UI must say so everywhere it matters.

KNOWN CONTRACT (verify against the code, then trust the code)
- GET /api/health returns status, data_mode, demo_session_id. GET /api/demo returns session_id, current_time, revision. POST /api/demo/reset restores fixtures and bumps revision.
- GET /api/jobs returns session_id, revision, jobs. Job fields: id, template (inference_batch | training_small | training_large), earliest_start, deadline, gpu_count, duration_hours, eligible_site_ids, status (queued | scheduled | running | completed | failed | unfulfilled), assigned_site_id, scheduled_start, completed_at, result_url, miss_penalty_usd, critical.
- POST /api/jobs takes template, earliest_start, deadline (UTC ISO). Server fills gpu_count, duration_hours and owner. 422 on a bad body. Reuse api.js apiRequest, datetimeLocalToUtcIso, toDatetimeLocalValue, formatUtc, setError exactly as they work today.
- GET /api/sites returns sites with site_id, name and hourly_profiles (hour_start, gpu_capacity, fixed_water_liters_per_hour, incremental_water_liters_per_gpu_hour, energy_kwh_per_gpu_hour, electricity_usd_per_kwh, water_cap_liters_per_hour or null).
- Planned and currently 501: POST /api/reallocation/preview (mode, natural_language_instruction, max_additional_cost_usd, emergency_restriction with site_id, water_cap_liters_per_hour, start, end), POST /api/reallocation/apply (preview_id, input_revision), POST /api/demo/advance. A preview response has preview_id, input_revision, status (feasible | infeasible), proposed_job_changes (job_id, old_placement, new_placement), metrics_before and metrics_after (total_water_liters, total_energy_kwh, total_cost_usd, jobs_on_time, jobs_late, jobs_unfulfilled), per_site_water (site_id, water_liters, water_cap_violations), cost_breakdown, deadline_outcomes (job_id, met_deadline, projected_completion), explanation, infeasibility_reason, simulated.
- Preview is stale when its input_revision differs from the current revision. Apply must send both preview_id and input_revision.
- Fixtures contain only two sites. Render exactly the sites the API returns. Never invent a missing site in live mode.
- If the API has no field for something the design shows (activity history, progress percent, result file name, per-site GPU utilization, hourly water per site), derive it only from real fields and label the basis, or show an honest unavailable state. Examples: GPU utilization is not returned, so compute assigned GPU count against the hour's gpu_capacity from jobs and sites and label it "GPU load from assignments"; hourly water is fixed plus incremental times assigned GPUs, labeled "modeled". Show JOB-014 style short labels by turning job-hackuta-0014 into JOB-014; keep the full id in a title attribute.
